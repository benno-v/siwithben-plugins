I found 12 issues. The most serious is a stored XSS in the dashboard: task text containing `{{DATA}}` gets the raw task JSON injected into the page as live HTML. The other big risks are the edit form quietly clearing due dates that aren't real dates, and dashboard changes getting refused, and pending ones dropped, after every sweep. No files were edited. I tried to confirm the first two issues in an in-memory Python session, but the command was blocked, so all findings come from reading the code.

1. **High: XSS through template placeholders** (`render_dashboard.py:156-162`). The page is built by running `str.replace` for each placeholder in order, and `PANELS` (task text) goes in before `DATA`, `CSS` and `JS`. `html.escape` leaves `{` and `}` alone. So a task action such as `{{DATA}} <img src=x onerror=alert(1)>` has `{{DATA}}` swapped for the raw JSON, and that JSON doesn't escape `<`. The `<img>` then runs in the page body. Sweeps copy text from emails and Slack, so this text can come from outside. A task containing `{{JS}}` or `{{CSS}}` also breaks the page. Fix: substitute every placeholder in one pass, for example with `re.sub` and a lookup dict.

2. **Medium: one string can break the whole dashboard** (`render_dashboard.py:144`). The inline JSON only replaces `</`. Task text with `<!--<script` puts the HTML parser into a state where the real `</script>` no longer closes the tag. The rest of the page, including the app script, is swallowed into the JSON element, `JSON.parse` fails, and none of the controls work. Fix: also escape `<`, `>` and `&` as `\u003c`, `\u003e` and `\u0026`.

3. **High: editing a task can delete its due date** (`render_dashboard.py:417, 436-440`). A due date that isn't a real date (`TBC`, `Fri`, `2026-02-30`) loads into the date field as `''`. The diff treats that as a change, so saving any edit, even just the owner, sends `due: ""` and clears the original text. The status dropdown has a similar bug (`:423`): a status that isn't in the list becomes `''`, the server then rejects the whole update (`apply_changes.py:73`), and the user's other edits are skipped.

4. **High: unrelated changes block dashboard changes** (`apply_changes.py:240`, `tasks_md.py:284`, `tasks_md.py:144-153`). The revision hash covers the whole file, including the `Last sweep:` line and the change log. Every scheduled sweep updates `Last sweep`, even when it adds nothing (`apply_changes.py:260-268`), so every pending dashboard block is then refused. Pending changes in the page are stored under a key that includes the revision (`render_dashboard.py:279`), so they vanish when the dashboard is re-rendered.

5. **Medium: `--force` overwrites newer edits** (`apply_changes.py:189-194, 255`). The `before` snapshot is only used for the report (`changed_rows`). With `--force`, an `update` writes over fields someone changed after the block was made. It should skip or flag fields where `before[f] != row[f]`.

6. **Medium: only one backup, overwritten on every write** (`tasks_md.py:344-345`). Each write replaces `TASKS.md.bak`, including sweeps that only change `Last sweep`. A few hourly runs after a bad apply, the only copy of the earlier state is gone. Rotating backups or naming them by timestamp would fix it.

7. **Medium: writes can break symlinks and permissions** (`tasks_md.py:346-350`). `os.replace` swaps a symlinked `TASKS.md` (for example into Dropbox or Obsidian) for a regular file, so the real target never gets updated. `mkstemp` also leaves the new file at mode `0600`, and there is no `fsync` before the rename, so a crash can leave an empty or partial file on some filesystems.

8. **Medium: edits made during an apply can be lost** (`apply_changes.py:232` vs `:277`). Nothing locks the file or checks that it hasn't changed between reading and the final write. A hand edit or a concurrent sweep in that window is overwritten. Re-reading and re-checking the revision just before `write_atomic`, or using a lock file, would close the gap.

9. **Medium: some rows are silently ignored** (`tasks_md.py:214-235, 196-206`). The table ends at the first line that doesn't start with `|`. So rows after a blank line, a second table, or rows written without a leading pipe go into the `outro` text. They're kept in the file but never parsed, validated or found by ID. Headings like `## Open tasks` or `## Done ✅` count as unknown sections. Their rows are invisible and an `add` creates a new `## Open` section.

10. **Low-Medium: sweeps re-propose rejected tasks** (`apply_changes.py:148-149`). The duplicate check skips Done rows, and rejected rows are only recorded in the change log. Each sweep can bring back a task that was already rejected or completed. Owners like `TBC` vs blank also aren't treated as the same, so `TBC` vs `""` slips past the check.

11. **Low: bad input crashes with a traceback** (`apply_changes.py:134, 175-176`; `render_dashboard.py:539`). These include `dict(op["fields"])` when fields isn't an object (and `dict(["ab"])` silently becomes `{'a': 'b'}`), `tm.is_date(123)` raising `TypeError` on a numeric `date`, and an invalid `--today`. They should be skipped or reported in the JSON summary instead.

12. **Low: duplicate IDs aren't handled safely** (`render_dashboard.py:141`; `apply_changes.py:265-277`). Duplicate IDs collapse in the dashboard's `tasks` map, so the page can show the wrong section and edit or snapshot the wrong row. `apply` still writes even when `validate` reports errors, and `find()` acts on the first match. Refusing to write when the input already has validation errors would be safer.

The rest of the escaping holds up. Python escapes all task text with `esc`, links in Source only allow `https?://` URLs with escaped `href`s, and the page script uses `textContent` and `setAttribute`. CRLF, a byte-order mark, `\|` inside cells and empty tables all parse correctly.
